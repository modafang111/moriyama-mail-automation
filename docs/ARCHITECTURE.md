この文書は、仕様を読んだうえで先に整理すべき項目への回答です。CSV書式は現時点では固定していません。依頼はウェブの専用フォームです。今の手作業の順番は `docs/操作手順.md` です。

## 今回作るシステムの全体構成

依頼受付と配信処理を分離します。受付方法が変わっても、Googleドライブ・配信対象・MyASP・履歴の中核はそのまま使えます。

```text
[依頼受付アダプタ]
  ウェブの専用フォーム（顧客がブラウザで開く。今は担当者PC。社外公開先は未確定）
        │
        ▼ 正規化した依頼（CampaignRequest）
[案件サービス]  ← 画面（GUI）はここだけを操作する
        │
        ├── Googleドライブゲートウェイ（アップロード・閲覧専用共有・URL取得）
        ├── 配信対象パーサ（CSV解析のみ。書式は後から差替）
        ├── 配信対象プロセッサ（追加、および今回の配信だけの除外）
        ├── MyASPゲートウェイ（第1段階はモック。次段階で実連携）
        ├── 担当者通知（このプログラムでは送らない。共通関数ができてから接続）
        └── 保存
              ├── 案件データ（ローカルSQLite）
              └── 配信履歴 / 操作ログ（ローカルSQLite）
```

1回のメルマガ配信を1案件として管理します。画面は案件の選択と進捗確認に集中し、本番配信だけは人間の明示承認を必須にします。

## 推奨する使用技術

| 用途 | 推奨 | 理由 |
| --- | --- | --- |
| 言語 | Python 3.11+ | Google Drive公式クライアントが安定。後のPlaywright連携も容易。この環境でテストしやすい。 |
| GUI | tkinter / ttk | Windows標準で追加ランタイムが少ない。専門知識がなくても使える単純画面向き。 |
| 保存 | SQLite（ローカル） | インストール不要。案件と履歴をファイル1つで扱える。Gitに含めない。 |
| 設定 | `.env` | 認証情報をソースに書かない。 |
| Googleドライブ | Drive API v3 | アップロード、`anyone` + `reader`、`webViewLink` 取得が公式に可能。 |
| MyASP | 第1段階はモック。次段階は MCP Connect を優先検討し、不足分はブラウザ自動操作 | 汎用REST APIは公開されていない。詳細は `MYASP_RESEARCH.md`。 |
| 依頼フォーム | ウェブの専用フォーム | 顧客がブラウザで開く。手順は `docs/操作手順.md`。社外公開先は未確定。 |
| 配布 | 当面は `D:\dev` 上のvenv起動。後でPyInstallerを検討 | 今は開発速度と検証を優先。 |

C# / Electron は採用しません。Drive APIと将来のPlaywrightを同じ言語で扱えることを優先しました。

## Windows上での実行方法

配置場所は指定どおり `D:\dev\moriyama-mail-automation` です。パソコンにフォルダが無い場合の手順は `docs/LOCAL_SETUP.md` です。

1. GitHub から ZIP を展開するか git clone する
2. `01_setup.bat` を実行する（`D:\dev` 作成、配置、初回セットアップ）
3. `03_start.bat` で操作画面を開く
4. 「ウェブフォームを開く」または `open_web_form.bat` で専用フォームを開く
5. 手作業の順番は `docs/操作手順.md`

データ本体（個人情報を含み得るDB）の既定場所は `%LOCALAPPDATA%\MoriyamaMailAutomation` です。プログラム本体とデータを分け、誤ってGitへ混ぜないようにします。`MORIYAMA_DATA_DIR` で変更できます。

## 案件データの保存方法

ローカルSQLiteの `campaigns` テーブルに、1配信=1行で保存します。

保存する主な項目:

- 案件ID、作成日時、更新日時
- 件名、本文、備考
- 資料のローカルパス、DriveファイルID、共有URL
- 配信対象の件数（追加・削除・除外）
- テスト配信先
- 配信モード（初期値はテスト）
- テスト配信結果、本番配信結果
- 状態、進捗フラグ
- 本番配信ロック（二重配信防止）

メールアドレスそのものは案件行には持たせず、同じローカルDBの `audience_entries` に分けて保存します。このDBファイルはGit管理外です。

## 配信履歴の保存方法

`delivery_history` に実行のたびに1行追加します。

- 実行日時
- 案件ID
- 件名
- テスト / 本番
- 配信対象件数、除外件数
- Googleドライブ共有URL
- 成功 / 失敗
- エラー内容（個人情報を含めない）
- 実行者名（`.env` の `OPERATOR_NAME`）

操作ログ `audit_log` には「誰がいつ何をしたか」を残します。メールアドレス一覧は書きません。

## Googleドライブとの連携方法

公式の Google Drive API v3 を使います。

1. 選択したPDF等をアップロードする（可能なら指定フォルダへ）
2. 共有権限を `type=anyone`, `role=reader` にする（閲覧専用、検索対象外）
3. `webViewLink` を取得して案件に保存する
4. 本文の `{{DRIVE_SHARE_URL}}` を置換するか、画面の挿入ボタンで貼る

認証は OAuth デスクトップアプリを想定します。クライアントJSONとトークンはローカルのみです。

認証ファイルがまだ無い場合は `GOOGLE_DRIVE_MODE=mock` で画面と履歴の流れを確認できます。モックは実ファイルをGoogleへ送りません。

## MyASPとの連携方法

2026-08-29 時点の公式情報では、第三者向けの汎用REST配信APIは確認できませんでした。あるのは次です。

- 管理画面操作（ログインURLは契約者ごとに異なる）
- CSV一括登録、ユーザー一覧からの削除・配信解除
- 一括配信メールの作成、テストメール送信、確認画面後の即時／予約配信
- Zapier（主に読者登録。配信実行そのものではない）
- MyASP MCP Connect（スタンダードプラン以上。下書き・テスト配信・予約配信など。即時配信と読者削除は非対応）

第1段階のプログラムは `MyAspGateway` インタフェースだけを呼び、実装はモックです。テスト配信は `.env` の `TEST_RECIPIENTS` にだけ送る前提で記録します（未設定なら実行できません。実送信はまだしません）。本番配信は確認画面と承認を通したあと、モックとして「予約配信した」と履歴に残すだけで、MyASPの読者全体へは送りません。

次段階では MCP Connect でできる操作を優先し、削除・即時配信など不足分だけブラウザ自動操作を検討します。画面セレクタを決め打ちした実装は、今は書きません。

## テスト配信と本番配信の安全設計

最優先は誤った一斉配信を防ぐことです。

- 配信モードの初期値は **テスト配信**。本番は初期選択しません。
- テスト配信は `.env` の `TEST_RECIPIENTS` のみ。案件の配信対象者へは送りません。
- 本番配信ボタンを押しただけでは送りません。最終確認画面が必須です。
- 確認画面には少なくとも、件名、配信モード、対象件数、除外件数、共有URL、本番であることの明示を出します。
- 承認には「本番配信を承認」と入力することを求めます。
- 本番配信済み案件はロックします。再実行時は警告し、既定では拒否します。
- 未選択のまま実行できません。
- 件名が空、または本文も共有URLもない状態では本番実行できません。

自動化してよいのは資料アップロード、URL取得、データ読み込みです。本番実行だけは必ず人の確認を挟みます。

## 個人情報と認証情報の管理方法

GitHubへ載せないもの:

- `.env`
- Google OAuthクライアント / トークン
- MyASPログイン情報・APIキー
- 顧客のメールアドレス一覧CSV
- 個人情報を含むDB・履歴ファイル

ログには件数とマスクしたメール（例: `a***@example.com`）だけを出します。アドレス一覧のダンプはしません。

将来、共通の通知処理をつなぐ場合も、配信対象者のアドレス一覧は入れません。案件ID、件名、作成日時、資料名程度に限ります。

1. **第1段階** 案件、ウェブ専用フォーム、Drive、対象データ読み込み口、テスト／本番の安全確認、予約配信前提、履歴、手作業の操作手順。通知メールは含めない
